## Calibração já feita pelo Planner (inspeção READ-ONLY do parquet real, só agregados — zero PII, zero linha individual)

O parquet real `data/staging/demanda_revelada_h3.parquet` tem **16.575 hexes** (9 colunas do contrato `demanda_revelada_v1`). Achados que fixam decisões do plano:

- **`dist_concorrente_lc_min_m` tem ZERO NaN no dado real** (todo hex tem ao menos uma célula com distância válida). Logo o tratamento de NaN é **defensivo** (não muda a contagem hoje), mas precisa estar definido no código para robustez futura.
- Máscara base `(n_concorrente_lc == 0) & (dist_concorrente_lc_min_m > 5000)` = **12.050 hexes**.
- Sweep de `LIMIAR_MEMBROS_GT5KM` sobre a base (contagem de hexes que sobrevivem):

  | limiar (`>=`) | hexes |
  |---:|---:|
  | 1 | 11.704 |
  | 5 | 4.993 |
  | 10 | 3.429 |
  | 25 | 1.928 |
  | 50 | 1.144 |
  | 100 | 621 |
  | 150 | 363 |
  | **200** | **229** |
  | 250 | 159 |

- **`LIMIAR_MEMBROS_GT5KM = 200` (inclusivo `>=`) → 229 hexes**, que reproduz a ordem de grandeza do protótipo (~231). É a **recomendação de default** do Planner (justificativa abaixo).

## Fórmula canônica fixada (nomes EXATOS do contrato `demanda_revelada_v1`)

```python
LIMIAR_MEMBROS_GT5KM = 200  # default calibrado (reproduz ~231 do protótipo → 229 hexes reais)

flag_vazio_competitivo = (
    (n_concorrente_lc == 0)                                   # sem unidade do concorrente LC no hex
    & (dist_ge_5km)                                           # ver tratamento de NaN abaixo
    & (membros_gt5km_concorrente_lc >= LIMIAR_MEMBROS_GT5KM)  # demanda expressiva a >5 km
)
```

- Colunas usadas do contrato (SÓ estas, zero coluna inventada): `hex_id`, `n_concorrente_lc`, `dist_concorrente_lc_min_m`, `membros_gt5km_concorrente_lc`. `membros` também é carregada para enriquecer o artefato (contexto de demanda total), não entra no filtro.

## DECISÃO 1 — tratamento de `NaN` em `dist_concorrente_lc_min_m` (registrada pelo Planner)

**Decisão: NaN é tratado como "muito longe" → INCLUI no vazio** (a condição de distância é `dist_concorrente_lc_min_m.isna() | (dist_concorrente_lc_min_m > 5000)`).

Justificativa:
1. Semântica: no ingestão, `dist_concorrente_lc_min_m = g["dist_sf_m"].min()`; NaN só ocorreria se NENHUMA célula do hex tivesse distância válida ao concorrente LC — ou seja, o concorrente é ausente/indeterminado nas proximidades, o que é coerente com "vazio competitivo", não com "concorrente perto".
2. Conservador em relação à contagem: no dado real há **0 NaN** e **0 hexes NaN com `n_concorrente_lc==0` e `membros_gt5km>0`**, então a escolha **não altera a contagem de 229 hoje**; é robustez para dumps futuros.
3. O Builder deve **materializar uma coluna booleana `dist_ge_5km`** (True quando `isna | >5000`) para deixar o critério auditável e testável em caso-limite.

## DECISÃO 2 — `LIMIAR_MEMBROS_GT5KM` (registrada pelo Planner)

**Default recomendado = `200` (comparação inclusiva `>=`).** Parametrizável (constante de módulo em `vazios_competitivos.py`, com a função aceitando `limiar_membros_gt5km: int = LIMIAR_MEMBROS_GT5KM`), para o operador poder afrouxar/apertar sem editar a fórmula.

Justificativa: reproduz a ordem de grandeza do protótipo (~231 → **229** hexes reais); é o ponto do sweep que casa; separa "demanda expressiva" de ruído (o percentil 75 da base é 12; 200 fica bem acima, selecionando só os hexes de demanda alta e distante). O Builder deve **reportar a contagem obtida no `completed.md`** e comparar com 229 como sanity check; divergência só é aceitável com justificativa de dado atualizado.
