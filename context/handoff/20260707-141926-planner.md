## Plano técnico

### 1) Estratégia latin-1 (regra geral, vale para os 2 arquivos)
1. O core font `Helvetica` do `fpdf2` codifica em **latin-1**, que cobre integralmente os acentos
   de letras portuguesas (á â ã à ç é ê í ó ô õ ú ü, maiúsculas incluídas: Á Â Ã À Ç É Ê Í Ó Ô Õ Ú Ü).
   Escrever essas letras acentuadas no texto-fonte é **seguro** e não precisa trocar fonte/lib.
2. `_ascii()` (`censo_report.py:170-172`, `relatorio_municipal.py:211-213`) **fica intocada na
   lógica** — segue fazendo `text.encode("latin-1", errors="replace").decode("latin-1")` como
   salvaguarda de último recurso. O que muda é só o TEXTO que entra nela.
3. A ARMADILHA real é tipografia **fora** de latin-1: travessão `—`(U+2014)/`–`(U+2013), bullet
   `•`(U+2022), seta `→`(U+2192), reticências `…`(U+2026), aspas curvas `“”‘’`
   (U+201C/D/U+2018/9) — todos viram `"?"` silenciosamente via `errors="replace"`. Regra de escrita:
   usar SEMPRE ASCII de pontuação (`-`, `"`, `(c)`, `...`, `->`) mesmo em texto com letras
   acentuadas. Nota: `©` (U+00A9) é tecnicamente latin-1 (0xA9) e renderizaria sem virar `"?"`, mas
   o backlog/§2 pede ASCII `"(c)"` por consistência — já é o padrão usado em `_ATRIBUICAO_TILES`
   ("(c) OpenStreetMap, (c) CARTO"); não regredir para `©`.
4. **Não mexer em números/separadores decimais** ao acentuar. O código já mistura, de forma
   pré-existente, `"1.5 km"` (ponto) em alguns textos com `"1,5 km"` (vírgula) em outros — isso é
   estilo numérico, NÃO é acentuação, e está fora do escopo desta epic. Testes existentes já
   travam literais como `b"1.5 km"`, `b"2.000"`, `b"3.000"` — não tocar esses valores/formatos,
   só as letras ao redor. Mudar separador decimal quebraria asserts sem motivo dentro do escopo.
5. Comentários-fonte de código (não voltados ao usuário) **não precisam** ganhar acento — só o
   ÚNICO comentário enganoso listado no item 3 abaixo precisa ser corrigido no CONTEÚDO técnico
   (latin-1 vs ASCII); manter o estilo sem-acento do restante dos comentários do arquivo para
   minimizar diff fora de escopo.

`_classico_credit_page` (linha 1022 de `censo_report.py`), um `link=url` construído por
`build_search_url()` (`src/motor_expansao/api/maps_geocoder.py:87-90`), que retorna
`"https://www.google.com/maps/search/?api=1&query=..."` — essa URL **contém um `"?"` legítimo de
sintaxe de URL** (não é erro de encoding; `url` não passa por `_ascii()`). Para o template
`classico`, o teste deve remover esse padrão conhecido antes de checar zero `"?"`:
```python
_QMARK_ALLOWLIST = (b"/maps/search/?api=1&query=",)  # sintaxe de URL do Google Maps (build_search_url); nao e artefato de encoding
scrubbed = pdf_bytes
for pattern in _QMARK_ALLOWLIST:
    scrubbed = scrubbed.replace(pattern, b"")
assert b"?" not in scrubbed
```
Builder deve, antes de travar essa allowlist, RODAR o gerador do template `classico` no estado
ATUAL (pré-edição) e confirmar empiricamente que todo `"?"` no PDF vem exatamente desse padrão
(contar ocorrências e inspecionar o contexto ao redor de cada `"?"`), documentando o achado no
commit/handoff do Builder. Não expandir a allowlist além do necessário.
