## DECISÃO TÉCNICA RESOLVIDA — `@st.cache_data` (com chave manual por tokens), NÃO `cache_resource`

**Escolha: `@st.cache_data`.** Justificativa verificada empiricamente (experimentos efêmeros
`python -c`, nada escrito em `src/`):

1. **`pdk.Deck` É picklável** (pré-requisito do `cache_data`, que serializa por pickle). Teste:
   `pickle.dumps(deck)` de um Deck real (Layer + ViewState + tooltip) → 894 bytes, `pickle.loads`
   OK, `to_json()` idêntico após roundtrip, e os atributos custom `_ultra_capped` /
   `_ultra_effective_cap` (setados pelos builders) SOBREVIVEM ao roundtrip. Logo o `cache_data` não
   quebra e o caption honesto do cap continua funcionando.
2. **`cache_data` retorna uma CÓPIA FRESCA a cada chamada** (verificado: dois hits do mesmo cache
   devolvem objetos distintos — `d1 is d2 == False` — e um `deck.layers.append(...)` no primeiro
   NÃO vaza para o segundo, que continua com o nº de layers original). Isto é **decisivo** porque
   `render_mapa_territorial` faz `deck.layers.append(_build_multihex_selection_layer(...))`
   (pages.py:4406) DEPOIS de obter o deck. Com `cache_data` esse append muta uma cópia por-chamada →
   o cache permanece limpo. Com `cache_resource` (retorna o MESMO objeto compartilhado entre reruns
   E entre sessões) esse append ACUMULARIA a layer de destaque no deck cacheado a cada rerun/sessão
   → bug visível + vazamento entre sessões. `cache_resource` exigiria lock manual e ainda sofreria
   esse bug de mutação.
3. **Escopo do cache**: `cache_data` é global ao processo mas chaveado pelos args → reuso entre
   sessões (bom hit-rate) COM isolamento de mutação (cópia por chamada). Sem os contras do
   `cache_resource`.

**Onde e como cachear:** NÃO decorar os 3 builders puros nem o dispatcher `build_unified_map_figure`
diretamente (mantê-los puros e testáveis). Criar um **wrapper novo cacheado**
`build_unified_map_figure_cached` em `components.py` que delega ao dispatcher.

**Assinatura do wrapper (chave de cache exata):**
```python
@st.cache_data(show_spinner=False, max_entries=MAP_FIGURE_CACHE_MAX_ENTRIES)  # SEM ttl= (D2)
def build_unified_map_figure_cached(
    _df: pd.DataFrame,                       # underscore => IGNORADO no hash (não hasheia o frame)
    _competitors_df: pd.DataFrame | None,    # idem
    _ultra_df: pd.DataFrame | None,          # idem
    _dominio_df: pd.DataFrame | None,        # idem
    *,
    color_mode: str,
    enabled_overlays: tuple[str, ...],       # tupla ORDENADA (membership-only no dispatcher)
    selected_ufs: tuple[str, ...],
    selected_cities: tuple[str, ...],
    selected_faixas: tuple[str, ...],
    search_pin: tuple[float, float] | None,
    search_hex_id: str | None,
    df_token: str,                           # sha1 leve do conteúdo de _df (identidade do recorte)
    competitors_token: str,                  # token de _competitors_df JÁ FILTRADO por rede
    ultra_token: str,
    dominio_token: str,
):
    return build_unified_map_figure(
        _df, color_mode=color_mode, enabled_overlays=list(enabled_overlays),
        selected_ufs=list(selected_ufs), selected_cities=list(selected_cities),
        selected_faixas=(list(selected_faixas) or None),
        competitors_df=_competitors_df, ultra_df=_ultra_df,
        search_pin=search_pin, search_hex_id=search_hex_id, dominio_df=_dominio_df,
    )
```
- **Por que underscore + tokens explícitos:** o Streamlit PULA o hash de parâmetros cujo nome começa
  com `_`. Assim não pagamos o hash caro de um DataFrame de 20k–290k linhas × ~40 colunas
  (imprevisível), e controlamos AUDITAVELMENTE a chave — mitiga o risco central ("nunca servir UF
  errada"). O `_df` é usado no cálculo mas a identidade vem do `df_token`.
- **Token do `df` (REV-04 H2, versão robusta):** `hashlib.sha1` sobre
  `pandas.util.hash_pandas_object(df["hex_id"], index=False).to_numpy().tobytes()`, com prefixo do
  `len(df)`: `f"n{len(df)}:{sha1_hexdigest[:16]}"`. `hash_pandas_object` é vetorizado em C (poucos ms
  mesmo em 290k) e sensível ao CONTEÚDO do `hex_id` (dtype object) — `.tobytes()` cru NÃO serve para
  object dtype. Recorte de UF/cidade/faixa muda o conjunto de `hex_id` → token muda → MISS correto.
  Valores de score são estáticos por hex dentro do processo (parquet `:ro`), então o conjunto de
  `hex_id` é fingerprint fiel do deck. Dois recortes com conjuntos de `hex_id` DIFERENTES têm hashes
  diferentes → **impossível false-hit entre UFs**. (Reordenação de linhas com mesmo conjunto geraria
  MISS espúrio — inofensivo, só recomputa; nunca false-hit.)
- **Helper genérico de token** `_map_frame_token(df, cols)`: None→`"none"`, vazio→`"n0"`, senão
  `f"n{len(df)}:{sha1(hash_pandas_object(df[cols_presentes]).to_numpy().tobytes())[:16]}"`. Usar
  `cols=["hex_id"]` p/ `df` e `dominio_df`; `cols=["rede","lat","lng"]` p/ competitors filtrado;
  `cols=["lat","lng"]` p/ ultra. O token de competitors DEVE ser calculado sobre
  `competitors_df_filtered` (pós-filtro de rede) — assim o filtro de redes invalida o cache.
- **`multihex_cenario` NÃO entra na chave** (a layer de destaque é anexada DEPOIS, pós-cache, em
  `render_mapa_territorial` — padrão atual em pages.py:4406). Add/remove de hex → HIT no builder.
- **`max_entries` (bound de memória — D2 proíbe TTL, NÃO tamanho máximo):** constante
  `MAP_FIGURE_CACHE_MAX_ENTRIES = 24` em `components.py` (path do ciclo; NÃO tocar `constants.py`).
  Rationale: cada entrada guarda `(deck, n)` picklado (~10–15 MB por deck, dominado pelas colunas de
  tooltip) → teto ~360 MB para uma sessão exploratória longa; ~6 recortes × 4 modos. Tunável pelo
  Builder se a medição indicar. NÃO é `ttl` → não viola D2.

## Riscos técnicos
- **Cache servir UF/filtro errado (risco central).** Mitigado pela chave por tokens explícitos
  (df/competitors-filtrado/ultra/dominio) + modo + overlays (tupla ordenada) + ufs/cities/faixas +
  search; e pelos testes de invalidação (passo 6) e anti-vazamento A→B→A (passo 8), ambos
  OBRIGATÓRIOS. Conjuntos de `hex_id` distintos ⇒ hashes distintos ⇒ false-hit entre UFs impossível.
- **Fragments aninhados (externo do mapa + interno do pydeck) e dois fragments irmãos na aba**
  (mapa + painel multi-hex). REV-05 sinaliza que a interação exata de reruns não foi testada
  headless. Comportamento esperado: clique no mapa → rerun do fragment interno (+ `st.rerun()` app
  na captura de clique novo, mantido); troca de modo/overlay → rerun do fragment do mapa; add/remove
  hex → rerun do painel (mapa NÃO reconstrói); "Atualizar mapa" → `st.rerun(scope="app")`. Validação
  headless dos corpos + validação VISUAL humana PÓS-QA.
- **Mudança de comportamento nos guards de modo indisponível/domínio.** Ao mover o `return` para
  DENTRO do `_render_mapa_fragment`, um modo indisponível pula só o MAPA (o fragment retorna) mas as
  expanders abaixo ainda renderizam — antes o `return` pulava a aba inteira. Mudança mínima e
  arguivelmente melhor; nenhum consumidor externo depende disso. O Builder deve grepar por teste que
  assuma o early-return da aba e ajustar se existir.
- **Memória sem TTL.** `max_entries=24` bound (~360 MB teto). D2 (sem TTL) preservado; `max_entries`
  não é TTL. Tunável se a medição pedir.
- **Leitores externos do modo de cor/overlay.** Verificado por grep em `src/`: NÃO há leitor de
  `session_state["mapa_territorial_color_mode"]` nem `["mapa_territorial_overlays"]` fora das duas
  definições de widget (pages.py:4318/4329). Mover para o fragment é seguro (session_state não é
  isolado por fragment; o valor continua disponível se algum consumidor surgir).
- **Falso ganho em sessão nova / recorte inédito.** O 1º render de cada recorte/modo continua pagando
  MISS (rebuild + to_json). Medir MISS (1º) separado de HIT (subsequentes) — não confundir com "cache
  não funciona".
