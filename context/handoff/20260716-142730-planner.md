## Decisões técnicas FECHADAS (não repassar ao Builder para decidir)

### D1 — Motor de render: **deck.gl `H3HexagonLayer` (standalone) — MapLibre NÃO usado no spike**
Recomendação fechada: **deck.gl `H3HexagonLayer`** via o bundle UMD standalone (`deck.gl@latest` por CDN), com **basemap raster CARTO dark via `TileLayer` do próprio deck.gl**. Justificativa curta:
- `H3HexagonLayer` **aceita `hex_id` cru** (`getHexagon: d => d.h`) e tessela a célula na GPU — **elimina** as 18–35k chamadas `h3.cellToBoundary` que o caminho Leaflet/h3-js do `ui_proto.py` faz em CPU e **remove a geometria do payload** (exatamente a vantagem que a emenda pede). É a diferença que o PoC Leaflet (~500 hexes) não pôde medir.
- Render WebGL/GPU é o que escala a dezenas de milhares de polígonos a ~60fps — é o "teto de performance" que o bloco quer medir; Leaflet (DOM/SVG) satura em milhares.
- Recolor (dor #2) = update de atributo GPU via `updateTriggers.getFillColor` — sem re-serialização; é a hipótese "recolor client-side" do REV-04 testável diretamente.
- Seleção/cenário (dor #3) = `pickable:true` + `onClick` no browser, sem rerun.
- **MapLibre NÃO entra no spike**: só agregaria basemap vetorial (style JSON + 2º bundle) sem mudar o número que interessa (throughput de polígonos H3). Fica registrado como opção viva para o REBUILD real (BLK-REV-12), não para este spike. **h3-js separado NÃO é necessário** — o bundle do `@deck.gl/geo-layers` já embute o h3; a viewport inicial é pré-computada em Python (bbox de lat/lng do recorte), então o cliente não precisa de h3 para nada.

Assina `version="ui_spike_deckgl_v1"`.
- **Cache ISOLADO:** `data/cache/ui_spike_deckgl/<UF>.json` — diretório NOVO, **não** reusar `data/cache/ui_proto/`. Já cai sob `data/cache/` do `.gitignore` (linha 67) → gitignored automático.
- **Opt-in:** `is_spike_enabled()` retorna True se `os.environ["ULTRA_SPIKE_DECKGL"]=="1"` OU `st.session_state.get("show_ui_spike_deckgl")`. (Espelha `is_proto_enabled()`; env var e chave DISTINTAS do proto.)

### D3 — Escala real 18–35k: de onde vêm os hexes e payload enxuto
- **Fonte:** `data/outputs/hexagonos_dashboard_enriquecido/uf=<UF>/parte-0.parquet` — o MESMO artefato derivado (NÃO oficial M1) que o dashboard de produção lazy-carrega por UF (`load_uf_slice`, CLAUDE.md §4). Confirmado: **SP tem 47.389 hexes** → exercita o cap real de UF grande. É READ-ONLY (leitura de parquet derivado; zero escrita em artefato M1).
- **Cap (espelha produção `components.py:1552`):** `effective_limit = MAP_POINT_LIMIT_LARGE (18000) if len(df) > MAP_POINT_LIMIT (35000) else MAP_POINT_LIMIT (35000)`. Ordena por `score_priorizacao` desc (estável) antes de `.head(limit)`. `mode_stress=True` desliga o cap (renderiza os ~47k crus de SP) só para achar o teto — opção, não default.
  - SP (47k>35k) → cap 18k (cenário LARGE real). UF de 18k–35k → cap 35k. Cobre as duas pontas do intervalo do bloco.
- **Payload mínimo por hex (chaves curtas, SEM geometria, SEM PII):** `h`=hex_id (str), `bm1`=banda M1 (int 0–9), `br`=banda residual (int 0–9), `s`=score_priorizacao (float), `sr`=score_oportunidade_residual (float), `p`=pop_total (int), `o`=oferta_efetiva_disponivel (int). Dois índices de banda pré-computados = recolor client-side sem novo payload. Sem `lat/lng` por hex (a célula vem do `hex_id`); a viewport inicial vai só uma vez em `data["view"]={"longitude","latitude","zoom"}` (bbox calculado em Python).
- **Colunas lidas do parquet:** `hex_id, score_priorizacao, score_oportunidade_residual, pop_total|populacao_proxy, oferta_efetiva_disponivel` (subset; fallback de leitura total se subset falhar, como `ui_proto.py`).

### D4 — Harness Playwright (parametrizável; NÃO auto-roda contra produção)
- **Arquivo:** `scripts/rev08_spike_playwright.py`. Dep já presente (`playwright>=1.44.0`, extra `[scraping]`, `pyproject.toml:98-99`) — **sem dep nova**.
- **CLI:** `--url` (default `http://localhost:8501`), `--uf` (default `SP`), `--flow {render,recolor,scenario,pdf,all}` (default `all`), `--runs N` (default 5), `--out <path.json>`, `--target {spike,production}` (default `spike`). **Nunca hardcoda produção**; produção só sob `--url https://dashboard.ultra-expansao.tech` explícito.
- **4 fluxos de dor cronometrados:**
  - **REV-03 render do mapa (dor #1):** dispara "gerar recorte" e lê `window.__spikeFirstPaintMs` (trigger→1º paint dos hexes).
  - **REV-04 troca de modo de cor (dor #2):** clica o toggle M1↔Residual, lê `window.__spikeRecolorMs`.
  - **REV-05 seleção/cenário múltiplo (dor #3):** adiciona N hexes ao cenário, lê `window.__spikeAddHexMs` por add (latência incremental).
  - **REV-06 geração de PDF (dor #4):** o SPIKE não gera PDF (é dor server-side do app real). Este fluxo é **exclusivo do `--target production`**: dirige o botão "gerar relatório"/download do Streamlit real e cronometra clique→arquivo via evento de download do Playwright. No `--target spike` o fluxo `pdf` é **pulado com aviso** (não inventar número).
- **O que MEDE:** deltas `performance.now()` expostos como `window.__spike*` + `page.on("download")`/wall-clock para o fluxo PDF; agrega mediana/p95 por fluxo e escreve JSON em `--out`. Loga claramente que **não** dispara contra `dashboard.ultra-expansao.tech` sozinho — o `--target production` é ação humana.
- **Guarda anti-produção:** se `--url` contém `ultra-expansao.tech` E não há flag explícita `--i-confirm-production`, o script **aborta com instrução** (impede a esteira autônoma de gerar tráfego real).
