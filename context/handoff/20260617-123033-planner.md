### MUDANÇA 2 — Tab selector sticky (NÃO depende do gate; planejada integralmente)

**Arquivo único:** `src/motor_expansao/dashboard/pages.py`, função `inject_styles` (140–407); bloco do `stSegmentedControl` em 318–356.

**Risco 2 avaliado:** `position: sticky` em um descendente só funciona se NENHUM ancestral entre o elemento e o viewport tiver `overflow` diferente de `visible`. No layout Streamlit o `.block-container` e o `section.main` em geral não cortam o scroll vertical (o scroll é do `stApp`/body), então `sticky` tende a funcionar. Porém é frágil entre versões. **Estratégia escolhida: sticky como caminho principal + reforço defensivo de `overflow: visible` nos contêineres do segmented control, mantendo `position: fixed` como FALLBACK documentado em comentário (não ativado por padrão, para não exigir padding compensatório que desloca todo o corpo).**

**Passo 2.1** — Dentro do bloco já existente que casa `div[data-testid="stSegmentedControl"]` (linhas 318–322), adicionar as regras de fixação. Editar esse seletor para:
```css
div[data-testid="stSegmentedControl"],
div[data-testid="stSegmentedControl"] > div {
    display: flex;
    gap: 8px !important;
}
/* BLK-UI-08: tab selector fixo no topo ao rolar. sticky depende de nenhum
   ancestral ter overflow!=visible; reforcamos visible no proprio container.
   Fallback (se algum tema cortar o scroll): trocar 'sticky' por 'fixed' +
   padding-top compensatorio no .block-container — NAO ativado por padrao. */
div[data-testid="stSegmentedControl"] {
    position: sticky;
    top: 0;
    z-index: 999;
    background: linear-gradient(180deg, #0E1324 0%, #0A0F1F 100%);
    padding-top: 0.4rem;
    padding-bottom: 0.4rem;
    overflow: visible;
}
```
- `z-index: 999` fica abaixo de popovers/menus do baseweb (que usam z-index muito alto) e acima do conteúdo das abas.
- `background` opaco evita que o conteúdo role POR TRÁS do seletor e fique visível (sem fundo, o sticky ficaria transparente). Usar o mesmo gradiente do `stApp`/sidebar para coerência visual.
- `top: 0` ancora ao topo da área de scroll.

**Passo 2.2** — NÃO alterar `render_tab_selector` (484–508) nem a ordem de chamada em `streamlit_app.py` (515–524). É mudança puramente de CSS.

**Passo 2.3 (teste)** — Verificação por presença de CSS no output de `inject_styles` (mesmo padrão de `test_inject_styles_cobre_componentes_baseweb`, linha 4735): capturar o markdown e assertar `"position: sticky"` (ou `"position:sticky"` tolerante a espaço) e `"top: 0"` presentes no bloco do `stSegmentedControl`. ## DECISÃO D1 — Fluxo endereço → coordenada (GATE HUMANO, decidir antes da Mudança 3)

O campo hoje aceita só lat/lng numérico. Para aceitar endereço livre, há 2 caminhos:

### Alternativa A — Offline, sem DEC (link clicável)
- **UX:** usuário digita o endereço → o dashboard monta o link de busca do Google Maps com `build_search_url` (função PURA, sem rede) → exibe um botão/link "Abrir no Google Maps" → usuário abre, copia a coordenada do pino e cola de volta no MESMO campo → a busca numérica resolve via `parse_coordinate_input`.
- **O que muda em `render_coord_search_sidebar`:** quando `parse_coordinate_input(raw)` der `None` e o texto for não-numérico, renderizar `st.link_button(..., build_search_url(raw))` + caption de instrução; retornar `None` nesse ramo.
- **Guardrail §2:** NÃO tensiona (zero rede no dashboard). NÃO exige DEC.
- **Custo:** 1 passo manual do usuário (não resolve automático).

### Alternativa B — Fetch HTTP puro, EXIGE nova DEC (resolução automática)
- **UX:** usuário digita o endereço → o dashboard faz uma requisição leve (só `urllib.request`, sem Selenium) à URL de busca do Maps, segue o redirect e extrai a coordenada via `extract_any_coord` → retorna `(lat,lng)` automaticamente. Sem internet/falha → fallback gracioso para o link clicável da Alt. A, sem exceção.
- **Guardrail §2:** TENSIONA ("não criar dependência de API ao vivo no dashboard de produção"). **Requer nova DEC**, nos moldes da DEC-004, com no mínimo:
  - (a) Escopo restrito: fetch SÓ no caminho de resolução de endereço da busca (NÃO na carga/interatividade do mapa nem em qualquer outro ponto do dashboard).
  - (b) Cache local gitignored (ex.: `data/cache/geocode/`) para minimizar requisições.
  - (c) Fallback offline gracioso: sem rede → link clicável da Alt. A; default seguro em CI/teste (sem rede), coberto por teste explícito com mock.
  - (d) Timeout curto e `try/except` amplo; a carga/interatividade offline do dashboard NÃO pode quebrar se a rede faltar.
  - (e) I/O isolado fora do dashboard (helper em `maps_geocoder.py`), import lazy.
  - (f) Atribuição/limites de uso e nota anti-PII (o endereço digitado é enviado a serviço externo — registrar na DEC).

### Recomendação técnica do Planner
**Recomendo a Alternativa A.** Ela entrega o valor pedido (campo aceita endereço e gera o caminho para a coordenada) reutilizando um helper PURO já existente, SEM tensionar o guardrail §2 e SEM o overhead/risco de uma nova DEC, fetch ao vivo, cache e LGPD. Se a resolução 100% automática for requisito de produto, a Alternativa B é viável mas só após DEC aprovada com as mitigações (a)–(f). A escolha é do humano.

> **O Builder só implementa a Mudança 3 após o humano escolher A ou B** (e, se B, após a DEC ser aprovada). As Mudanças 1 e 2 NÃO dependem do gate e estão planejadas integralmente.
