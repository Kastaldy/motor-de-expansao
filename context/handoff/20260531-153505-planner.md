**Conclusão da reprodução (CORREÇÃO ao diagnóstico do backlog):** a quebra NÃO depende de versão de
pydantic/pandas/numpy. Ela ocorre porque, no CI, `pydantic_settings` está SÓ no extra `api` (não
instalado), então roda o RAMO FALLBACK (`else`, linhas 99–164). O `__init__` desse ramo
(linhas 145–150) itera `self.__class__.__dict__.items()` e faz `setattr` para todo nome `isupper()`;
`CORES` (linhas 152–164) é `@property` cujo nome é `isupper()`, e property sem setter explode no
`setattr`. **Logo: pinar libs (Opção A pura) NÃO conserta o CI** — o ramo que falha sequer importa
pydantic. O conserto obrigatório é no `config.py` (Opção B). A causa "pydantic novo" do backlog
(linhas 152–157) está incorreta para o CI.

**Repro 3 — validação da correção mínima proposta (isolada, sem editar o repo):** com o guard
`if isinstance(default, property): continue` no loop do `__init__`, `Settings()` instancia, `CORES`
resolve com as 9 cores, e o override por env das chaves reais (`H3_RESOLUTION=9` → int 9) continua
funcionando. Comportamento de `Settings`/`CORES` preservado.

## Decisão de abordagem: HÍBRIDA (B como cura + elementos de A para paridade)
- **B (obrigatória, cura o CI):** corrigir o `__init__` do ramo fallback para PULAR descritores
  `property` (não só `CORES`, qualquer property futura). Mudança mínima, sem alterar semântica.
- **A (paridade/higiene, não é a cura):** pinar com TETO as libs de runtime e as ferramentas de
  qualidade no `pyproject.toml`, para o CI parar de puxar pandas 3.x / numpy 2.4.x / ruff novo e
  divergir do local. Sem teto, futuras releases reabrem o drift.
- **`ci.yml`:** rodar `ruff check . --no-cache` (cache deu falso-verde antes) e NÃO instalar o extra
  `api` (manter o fallback como caminho suportado e TESTADO — ver teste novo). Não adicionar `api`
  ao CI: isso mascararia o fallback em vez de corrigi-lo, e `api` está fora do deploy.

   (linha 147–148), o guard:
   ```python
   if isinstance(default, property):
       continue  # properties calculadas (ex.: CORES) nao recebem setattr
   ```

## Riscos técnicos
- **mypy/ruff floor:** versões locais foram medidas em Python 3.14 (não-CI). Pinar `==` numa versão
  possivelmente não-pública reprovaria o `pip install` no CI 3.11. Por isso o plano usa FAIXAS com
  teto, e o Builder calibra o floor pelo que o CI 3.11 instala. NÃO pinar `mypy==2.1.0`.
- **Tetos podem esconder incompat futura** (dívida adiada): mitigado por serem tetos amplos
  (`<3`, `<2.4`) e por a cura real (Opção B) não depender de versão.
- **Reimportação no teste** pode contaminar `sys.modules` se o teardown falhar — exigir restauração
  explícita e rodar a suíte completa para confirmar ausência de efeito colateral.
- **Paridade Python:** local 3.14 vs CI 3.11 permanece (fora de escopo mudar o CI p/ 3.14); registrar
  como observação para QA não estranhar contagens.
