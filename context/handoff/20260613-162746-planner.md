## Decisões tomadas

### D1 — Caminho de receita: Caminho B (3 fontes de receita)

**Decisão:** Adicionar `alunos_agregadores` (default 651), `ticket_agregador` (default R$82) e
`personal_mes` (default R$5.000) como parâmetros explícitos de `viabilidade()`.

**Justificativa:** O benchmark spec §8.2 (~23% EBITDA no ano 2+) é calculado com as 3 fontes de
receita do Excel. Com apenas balcão + custos fixos absolutos reais (pessoal R$50.128 + outros
R$38.150 = R$88.278/mês), a margem no cenário padrão (938 alunos × R$137) fica negativa
(~−13%), impossibilitando qualquer validação sem circularidade. O Caminho B é o único que:
(a) é fiel ao modelo do Excel, (b) permite benchmark sem ajustar artificialmente os custos,
(c) mantém a assinatura extensível. O Caminho C (parâmetro flat `receita_adicional_mes`) é
menos fiel e não distingue as fontes para análises futuras.

As 3 fontes têm tratamento independente: balcão passa por churn + inadimplência; personal é
fixo mensal (sem churn nem inadimplência); agregadores passam por inadimplência mas NÃO por
churn (o Excel os modela separadamente). Ver seção "Lógica de receita" abaixo.

### D2 — Custos fixos absolutos: config.py do módulo (D2b)

**Decisão:** Adicionar ao `src/motor_expansao/dimensionamento/config.py` as constantes dos
custos fixos absolutos, com comentário documentando a linha de origem no Excel/DRE/Fopag.

**Justificativa:** D2b centraliza os valores em um único arquivo nomeado (rastreável e
manutenível), mantém `simulador.py` limpo (importa de `config.py`), e os testes podem importar
as constantes para asserções sem duplicar números. D2a (hard-codar em `simulador.py`) divide
contexto. D2c exige editar o JSON (READ-ONLY). Nenhuma dessas constantes entra no `config.py`
raiz do M1 (guardrail preservado).

### D3 — Leitura do simulador_estrutura.json: constantes pré-extraídas em config.py (D3b)

**Decisão:** Os ratios do JSON são pré-extraídos e gravados como constantes nomeadas em
`config.py` do módulo. `simulador.py` importa apenas de `config.py` — zero I/O em runtime.

**Justificativa:** D3a (chamar `extrair_coeficientes_dre()` em runtime) cria dependência de I/O
no simulador, complica o mock em testes e viola o princípio de que o simulador é puro Python
sem efeitos colaterais. D3b mantém o simulador testável sem fixtures de arquivo. O
`simulador_parser.py` permanece READ-ONLY (é o contrato do BLK-DIM-00); os valores que ele
extraiu já estão em `simulador_estrutura.json` e são simplesmente transcritos para `config.py`
com referência à célula de origem.

## Lógica de receita (modelo fiel ao Excel)

O Excel modela 3 linhas de receita bruta independentes:

```
receita_balcao   = pagantes_balcao * ticket_balcao * (1 - inadimplencia)
                   onde pagantes_balcao = alunos_maturidade * (1 - churn)

receita_personal = personal_mes   # fixo; sem churn nem inadimplencia no Excel

receita_agr      = alunos_agregadores * ticket_agregador * (1 - inadimplencia)
                   # agregadores NÃO têm churn separado no Excel (valor de maturidade direto)

faturamento_total = receita_balcao + receita_personal + receita_agr
```

Deduções e impostos incidem sobre `faturamento_total` (base unificada).

Custos fixos absolutos (mensais, constantes em todo o horizonte):
- `pessoal_mes` = R$50.128 (Fopag, linha DRE 55)
- `outros_fixos_mes` = R$38.150 (IPTU R$2.000 + Água/Luz R$17.000 + Telefone R$500 +
  Limpeza R$14.000 + Tecnologia R$2.150 + Assessorias R$2.500 + Outros R$2.000; linhas DRE 52-59,69)

Aluguel é parâmetro separado (não embutido em `outros_fixos_mes`).

class ViabilidadeResult:

    receita_pos_impostos: float        # receita_liquida - (PIS+COFINS+ISS)

    m2: float,                         # metragem da unidade em m²
    aluguel_mes: float,                # aluguel mensal em R$

    alunos_agregadores: float = SIM_ALUNOS_AGREGADORES_MATURIDADE,  # default 651
    ticket_agregador: float = SIM_TICKET_AGREGADOR,                  # default R$82
    personal_mes: float = SIM_PERSONAL_MES_RECEITA,                  # default R$5.000
    # Parâmetros de churn / inadimplência
    churn: float = SIM_CHURN,                   # default 0.06
    inadimplencia: float = 0.02,                # não está no JSON; default do spec

    cartoes_pct: float = SIM_CARTOES_PCT,
    devolucoes_pct: float = SIM_DEVOLUCOES_PCT,
    # Impostos (regime presumido; defaults do JSON)
    pis: float = SIM_PIS,
    cofins: float = SIM_COFINS,
    iss: float = SIM_ISS,
    ir_efetivo: float = SIM_IR_EFETIVO,
    csll_efetivo: float = SIM_CSLL_EFETIVO,

**Nomes distintos para evitar colisão:**
- `personal_mes` (parâmetro de receita) vs `pessoal_mes` (parâmetro de custo)
- Para o Builder, usar `SIM_PERSONAL_MES_RECEITA = 5_000` e `SIM_PESSOAL_MES = 50_128.16`

## Lógica interna do DRE (implementação sugerida para o Builder)

```python
# 1. Pagantes balcão (churn aplica-se ao balcão)
pagantes_balcao = alunos_maturidade * (1.0 - churn)

# 2. Receitas brutas (3 fontes independentes)
receita_balcao  = pagantes_balcao * ticket_medio * (1.0 - inadimplencia)
receita_agr     = alunos_agregadores * ticket_agregador * (1.0 - inadimplencia)
receita_personal = personal_mes       # fixo, sem churn nem inadimplência
faturamento     = receita_balcao + receita_agr + receita_personal

# 3. Deduções (sobre faturamento total)
devolucoes      = faturamento * devolucoes_pct
receita_liquida = faturamento - devolucoes

# 4. Impostos (sobre receita_liquida)
total_impostos  = receita_liquida * (pis + cofins + iss)
receita_pos_imp = receita_liquida - total_impostos

# 5. Custos operacionais variáveis (% sobre receita_liquida)
custos_variaveis = receita_liquida * (
    royalties_pct + marketing_pct + manutencao_pct + cartoes_pct
)

# 6. Custos fixos absolutos
custos_fixos    = pessoal_mes + outros_fixos_mes + aluguel_mes

# 7. EBITDA
total_custos_op = custos_variaveis + custos_fixos
ebitda          = receita_pos_imp - total_custos_op

# 8. Margem EBITDA (sobre faturamento bruto, consistente com spec §8.2)
margem_ebitda_pct = ebitda / faturamento if faturamento > 0 else 0.0

# 9. IR e CSLL (sobre receita_liquida, regime presumido)
ir   = receita_liquida * ir_efetivo
csll = receita_liquida * csll_efetivo
lucro_liquido = ebitda - ir - csll

# 10. Capex
if capex is None and coef_capex_m2 is not None:
    capex = coef_capex_m2 * m2
elif capex is None:
    capex = SIM_CAPEX_DEFAULT

# 11. Rampa de maturação (payback)
# A rampa afeta SOMENTE balcão (alunos_inicial → alunos_maturidade).
# agregadores e personal mantêm valor constante durante a rampa (fiel ao Excel).
fcf_acum = -capex
payback_meses = float("inf")
for t in range(1, 61):
    frac   = min(t / max(maturacao_meses, 1), 1.0)
    al_t   = alunos_inicial + (alunos_maturidade - alunos_inicial) * frac
    pag_t  = al_t * (1.0 - churn)
    fat_balcao_t = pag_t * ticket_medio * (1.0 - inadimplencia)
    fat_agr_t    = alunos_agregadores * ticket_agregador * (1.0 - inadimplencia)
    fat_t   = fat_balcao_t + fat_agr_t + personal_mes
    dev_t   = fat_t * devolucoes_pct
    rl_t    = fat_t - dev_t
    imp_t   = rl_t * (pis + cofins + iss)
    rpi_t   = rl_t - imp_t
    cvar_t  = rl_t * (royalties_pct + marketing_pct + manutencao_pct + cartoes_pct)
    cfix_t  = pessoal_mes + outros_fixos_mes + aluguel_mes
    eb_t    = rpi_t - cvar_t - cfix_t
    ir_t    = rl_t * (ir_efetivo + csll_efetivo)
    fcf_t   = eb_t - ir_t
    fcf_acum += fcf_t
    if payback_meses == float("inf") and fcf_acum >= 0:
        payback_meses = float(t)

# 12. ROIC
nopat_anual = lucro_liquido * 12.0
roic_anual  = nopat_anual / capex if capex > 0 else 0.0

# 13. flag_viavel
flag_viavel = (margem_ebitda_pct >= 0.10) and (payback_meses <= 60)
```

## Plano de testes des-circularizados

### Princípio anti-circularidade

O spike validava a margem contra constantes que foram calibradas para bater. O BLK-DIM-03R deve
validar a margem contra o benchmark EXTERNO do Excel (spec §8.2), cujo valor (~22% no mês 12)
foi calculado com os defaults reais do Excel — não com os parâmetros do nosso código.

Critério de aceite: com os defaults do Excel (938 balcão, 651 agr, R$137, R$82, R$5.000
personal, custos fixos reais, aluguel R$20.000), a margem EBITDA deve ficar em **[18%, 26%]**.
A tolerância ±4pp em torno de 22% acomoda diferenças menores de arredondamento e modelagem
(churn aplicado sobre agregadores vs. não), sem ser trivialmente satisfeita por qualquer modelo.

O teste documenta que o valor esperado vem do Excel, não do código:
```python
# Margem esperada pelo Excel no mês 12: ~22% (spec §8.2 cita "~23% ano 2+")
# Tolerância ±4pp: [18%, 26%]
# Este intervalo é derivado do modelo do Excel, não das constantes do código.
```

## Advertências para o Builder

1. **Nomes `pessoal_mes` vs `personal_mes`:** são DIFERENTES — `pessoal_mes` é CUSTO (R$50k
   de folha), `personal_mes` é RECEITA (R$5k de personal trainer). Nomear as constantes como
   `SIM_PESSOAL_MES` e `SIM_PERSONAL_MES_RECEITA` para distinguir visualmente.

2. **Keyword-only após `*`:** a assinatura de `viabilidade()` usa `*` para separar os 4
   parâmetros posicionais dos demais. Os helpers `aluguel_teto`, `alunos_minimos_viaveis` e
   `m2_otimo` passam os extras via `**kwargs` — isso funciona automaticamente.

3. **Rampa de maturação:** `alunos_inicial` e `maturacao_meses` afetam SOMENTE o balcão na
   rampa. Os agregadores (`alunos_agregadores`) e `personal_mes` ficam constantes durante a
   rampa (fiel ao Excel). Não aplicar a rampa aos agregadores.

4. **`alunos_inicial` no `alunos_minimos_viaveis`:** o helper extrai `alunos_inicial` de
   `kwargs` com fallback para `float(SIM_ALUNOS_INICIAL)`. Não quebrar se ausente.

5. **Margem sobre faturamento bruto:** `margem_ebitda_pct = ebitda / faturamento_total` onde
   `faturamento_total` inclui as 3 fontes. Não dividir só pela receita de balcão. Isso é
   consistente com spec §8.2 ("sobre receita bruta") e com o teste de benchmark.

6. **Sem I/O em `simulador.py`:** o arquivo importa apenas de `config.py` e da stdlib. Nenhuma
   leitura de JSON, Parquet ou chamada de rede. Os testes devem rodar offline sem fixtures de
   arquivo.

7. **`test_payback_infinito_capex_alto`:** com os defaults (capex=2.34M, FCF steady ~19k/mês),
   `60 × 19k = 1.14M < 2.34M` → payback NUNCA dentro de 60 meses → `float("inf")`. Este teste
   é DIFERENTE do spike (que com custos proporcionais tinha FCF maior).

8. **`m2_otimo` internamente chama `viabilidade()` sem kwargs:** usa os defaults `SIM_*` das
   3 fontes de receita. Com `alunos_agregadores=651` e `personal_mes=5000` nos defaults,
   m2 não afeta a receita (só aluguel e capex) → a busca de m2 ótimo opera sobre a margem
   como função de (aluguel×m2 + capex×m2). O comportamento do spike está correto aqui.

9. **`__init__.py` do módulo:** expor as novas exportações do `simulador.py` após criação, se
   for necessário para integração futura. Por ora pode ficar com o docstring existente sem
   importar nada (os testes importam diretamente do submódulo).

10. **Ruff/mypy:** garantir que `float | None` e `int` nos tipos do dataclass estejam
    corretos. O `from __future__ import annotations` já está no spike — manter.
