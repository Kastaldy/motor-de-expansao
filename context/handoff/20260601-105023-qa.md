## Problemas médios (não bloqueadores)
- **Caption pode mentir na janela 18k–35k.** Em `pages.py:2539-2540`, `capped = n_points >=
  MAP_POINT_LIMIT_LARGE` e `effective_cap = 18000 if n_points >= 18000 else 35000`. Para um recorte com
  N hexes DISTINTOS no intervalo `18000 <= N < 35000` (ex.: 20.000 — exatamente o caso de
  `test_uf_pequena_nao_regride_cap_cheio`, que prova `n == total == 20000`, render SEM corte), o caption
  exibe "Mostrando os 18.000 hexagonos de maior prioridade ... recorte total maior que o limite de
  renderizacao" embora TODOS os 20.000 tenham sido renderizados e NADA tenha sido amostrado. É uma
  imprecisão cosmética numa feature cujo objetivo declarado é justamente "caption honesto". Não causa
  OOM, não toca M1/score, e foi a heurística explicitamente escolhida pelo Planner (passo 5.2, para não
  mudar a assinatura `(deck, n)` dos builders). Correção sugerida (bloco futuro ou follow-up): expor o
  cap efetivamente aplicado pelo builder (retornar/derivar de `len(key) > MAP_POINT_LIMIT`) em vez de
  inferir por `n_points`. Não-bloqueante: o fix do OOM em si está correto e os testes de cap são exatos.
