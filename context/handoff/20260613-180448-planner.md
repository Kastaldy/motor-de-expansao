## Objetivo do bloco (BLK-DIM-06)

Criar `backtest_dim.py`: harness que roda o motor de dimensionamento "às cegas" sobre os
54 maduros REAIS e reporta MAPE / RMSE / R² **out-of-sample** por camada e end-to-end, com

erro MEDIDO, não afirma um veredito.

## Decisões tomadas

### D1 — Tratamento do aluguel: **(a) usar `SIM_ALUGUEL_MES` como default + flag `aluguel_estimado=True`**
O parquet não tem `aluguel_mes` por unidade. Decisão (a) recomendada pelo BO: usar a constante
`SIM_ALUGUEL_MES` (R$20.000) para TODAS as unidades, com flag explícita no resultado e no
relatório. Justificativa: o aluguel **não afeta o faturamento bruto** (só custos/EBITDA/payback;
ver `simulador.py` linha 233-244). Como o alvo PRINCIPAL e mais honesto do backtest é
`faturamento_mensal_steady` vs `faturamento` real, o aluguel default NÃO contamina a métrica
central. Para EBITDA/margem/payback (secundários), o aluguel fixo é um confound documentado.
Não excluímos a Camada 4 (opção b) — perderíamos a análise; mantemos com flag.
- Parâmetro: `aluguel_default: float = SIM_ALUGUEL_MES` na assinatura.
- Campo no resultado: `aluguel_estimado: bool = True` (sempre True neste bloco).

### D2 — Ticket médio: **usar o `ticket_steady` REAL por unidade**
O parquet `base_calibracao_maduras.parquet` TEM `ticket_steady` real por unidade (mediana de
`ticket_medio_pagantes` da growth_api — handoff BO §"Campos reais", linha 30). Usar o real.
Fallback só para linha com `ticket_steady` ausente/<=0 → `SIM_MENSALIDADE_BALCAO` (137), com
contagem reportada. Não default global.

### D3 — Baseline = faturamento médio dos maduros (constante por fold LOO)
Para CADA camada o baseline é a previsão **ingênua da média**:
- Camada 1: baseline = média LOO de `pagantes` (média dos 53 de treino por fold) → R²/MAPE.
- Camada 3+4 (sem LOO, DRE determinístico): baseline = média de `faturamento` real (constante
  global). O R² já é "vs média" por definição (SS_res / SS_tot com média global).
- End-to-end (LOO): baseline = média LOO de `faturamento` real (média dos 53 de treino por fold).
Regra de leitura: **se MAPE do modelo > MAPE do baseline → o motor é pior que o chute ingênuo**.
O resultado expõe `mape_baseline` e `r2` (já é "vs média") lado a lado.

## Armadilhas e guardrails (LISTA EXPLÍCITA — ler antes de codar)

1. **Churn em percentual.** `churn_steady` no parquet está em PERCENTUAL (2.0–6.0). O simulador
   espera FRAÇÃO (0.02–0.06). Converter SEMPRE: `churn_fracao = churn_steady / 100.0`.
   Sem isso, `alunos_maturidade = pagantes / (1 - 3.8) < 0` → resultado absurdo.
   Helper dedicado `_churn_para_fracao` + teste `test_backtest_camada34_corrige_churn_percentual`.

2. **`alunos_maturidade` vs `pagantes_steady_state`.** O simulador faz internamente
   `pagantes_balcao = alunos_maturidade * (1 - churn)`. `pagantes_steady_state` já é PÓS-churn.
   Para alimentar o simulador com os pagantes reais, INVERTER:
   `alunos_maturidade = pagantes_steady_state / (1 - churn_fracao)`.
   Guard: se `(1 - churn_fracao) <= 0` (churn>=100% — não deve ocorrer pós-conversão), pular linha
   (conta como linha removida, reportada). Helper `_alunos_maturidade_de_pagantes`.

3. **Alvo NUNCA vem do próprio simulador.** O alvo é o campo REAL (`faturamento`,
   `pagantes_steady_state`). Proibido comparar saída do simulador contra outra saída do simulador.
   Teste `test_sem_dado_autogerado` guarda isso (ver fixtures).

4. **`alunos_agregadores=0` no backtest.** `pagantes_steady_state` é BALCÃO (sem agregadores).
   Para não inflar o faturamento previsto com agregadores fictícios, passar `alunos_agregadores=0.0`
   ao `viabilidade()`. Consequência: o faturamento previsto SUBESTIMA o real (que inclui agregadores
   + personal). Documentado como confound. (Nota: `personal_mes` mantém o default SIM=R$5.000 — é
   receita fixa real do modelo Ultra; só agregadores zeramos por não ter o split steady-state real.)
   `personal_mes=SIM_PERSONAL_MES_RECEITA` (default; não zerar).

5. **R² in-sample BANIDO como desempenho** (spec §7 / DEC-008). Camada 1 reporta R²/MAPE LOO.
   Camada 3+4 (DRE determinístico, sem parâmetros calibrados) reporta R²/MAPE sobre as 54 (não há
   LOO a fazer num cálculo sem fit). Esse R² é "vs média" (honesto), não in-sample de um fit.

6. **Erro alto é o OBJETIVO, não defeito.** Camada 1 já deu NO-GO (`r2_loo_log=-0.0134`). O
   end-to-end propaga isso → MAPE esperado >50%. A `nota` deve DOCUMENTAR, não minimizar.

7. **MAPE robusto a zero/NaN.** MAPE = `mean(|pred - real| / |real|)` só sobre `real != 0` e ambos
   finitos. Se nenhum válido → `float("nan")`. Helper `_mape` (ver assinatura). Nunca dividir por 0.

8. **Sem I/O nos testes.** Fixtures sintéticas seed-fixo. O `__main__` (não testado, `# pragma: no
   cover`) lê o parquet real e escreve `data/analysis/backtest_dim.md`.

9. **`data/analysis/backtest_dim.md` é GITIGNORED.** NUNCA commitar. Só materializado pelo
   `escrever_relatorio` chamado no `__main__`.

10. **loop_guard.** Zero diff em `config.py` raiz, `pipelines/m1/`, artefatos oficiais, VPS, CI.
    Só constantes LOCAIS de `dimensionamento/`. Importar `SIM_ALUGUEL_MES`,
    `SIM_MENSALIDADE_BALCAO`, `SIM_PERSONAL_MES_RECEITA` de `dimensionamento.config` (não redefinir).

11. **Camada 1 LOO reimplementado localmente (não chamar `calibrar_aderencia` por fold só para o
    R²).** Para o backtest da Camada 1 no espaço de ALUNOS precisamos das PREDIÇÕES LOO ponto-a-ponto.
    `calibrar_aderencia` faz LOO interno mas NÃO devolve o vetor de predições. Solução: implementar
    o LOO explicitamente no harness — para cada fold, `calibrar_aderencia(df_treino)` nos 53 e
    `prever_aderencia(pop_i, renda_i, modelo)[0]` no ponto deixado de fora. Isso REUSA as funções
    congeladas (não as altera) e dá o vetor de predições real out-of-sample. É também exatamente o
    que o end-to-end já faz na Camada 1 — fatorar num helper `_prever_loo_alunos`.

### Notas de implementação ponto a ponto

- **`_prever_loo_alunos`**: primeiro filtre as linhas válidas (pop/renda/pagantes finitos e >0),
  reset_index. Para `i` em `range(n)`: `df_treino = df_valido.drop(index=i)`;
  `modelo = calibrar_aderencia(df_treino)`; `pred_i, _, _ = prever_aderencia(pop_i, renda_i, modelo)`;
  `flag_i = modelo.flag_extrapolacao(pop_i, renda_i)`. Guard: se `n < N_MIN_BACKTEST` → `ValueError`.
  Atenção: `calibrar_aderencia` exige >= `N_MIN_CALIBRACAO` (5) linhas no treino — com n>=6 cada fold
  treina em n-1>=5 → ok. Se n==5, treino=4 < 5 → o fold falha. Por isso `N_MIN_BACKTEST=6` no harness
  para o LOO da Camada 1? **NÃO** — o BO pede N=5 nas fixtures. Solução: as fixtures de teste usam
  **n=8** para o backtest da Camada 1/end-to-end (treino=7 >= 5). `test_..._retorna_metricas` usam
  n>=6. Use `N_MIN_BACKTEST=5` como piso de ENTRADA, mas documente que o LOO requer treino>=5
  (logo n>=6 efetivo). Fixtures abaixo já respeitam isso (n=8).
- **Validação de colunas**: cada `backtest_camadaX` valida `set(COLS_X) - set(df.columns)` →
  `ValueError` claro se faltar.
- **MAPE/RMSE/R²**: operam sobre arrays numpy já filtrados (finitos). Mantenha NaN-safe.
- **`nota` por camada**: monte a string com os números medidos (`f"MAPE={mape:.1%} ..."`) + 1 frase
  honesta. Para camada1/end_to_end inclua "NO-GO esperado; erro propaga". NÃO afirme veredito fixo
  que contradiga os números.

    """O alvo do backtest e SEMPRE o `faturamento` real do df, nunca uma saida do simulador.
