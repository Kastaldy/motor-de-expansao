## Entendimento da tarefa
BLK-SEC-01 fecha o gap central: `docker-publish.yml` hoje publica no GHCR a CADA `push` em
`main` **sem depender do CI** (não há `needs:` nem `workflow_run`). Resultado: um commit com teste
quebrado / dep comprometida vira `:latest` que a VPS puxa. O bloco:
1. acopla o publish ao sucesso do CI;
2. garante tag por SHA (já existe via `type=sha`);
3. faz o `docker-compose.prod.yml` deixar de usar `:latest` cego (pin por digest/SHA conhecido);
4. cria runbook de rollback PULL (sem rebuild) em `docs/infra_producao.md` e alinha a seção antiga
   `--build` ao modelo PULL.

**Este bloco é exclusivamente CI/CD + infra de publicação. NÃO toca M1, `score_priorizacao`,
`hex_score_estrutural`, pesos (renda=0.40/pop=0.60), carteira, plano, fórmula nem nenhum artefato
oficial do M1.** Parâmetros canônicos (H3_RESOLUTION=7, DIST_MIN_ULTRA_KM=1.0, RENDA_MIN=4500.0)
não são tocados.

## Decisões de escopo (tomadas pelo Planner — o Builder NÃO decide isto)

### D1 — Acoplamento ao CI: **OPÇÃO B (workflow único, `needs: [test]`)** — CONFIRMADA
Confirmo a recomendação do Block Orchestrator. Razões:
- `needs: [test]` é garantia nativa e legível: o job `publish` só roda se `test` concluiu com
  sucesso. Sem isso, todo o job (e seus steps de push) é pulado.
- O SHA é `github.sha` correto, sem o malabarismo de `head_sha`. Evita a armadilha da Opção A
  (em `workflow_run`, `github.sha`/`actions/checkout` apontam para o head do default branch, não
  para o commit testado → risco de buildar/taguear o commit errado).
- Mantém um só lugar de verdade para o gate.

**Estrutura concreta:** fundir o job de publicação DENTRO de `.github/workflows/ci.yml` como um
segundo job `publish`. O arquivo `.github/workflows/docker-publish.yml` é **removido** (`git rm`)
para não restar caminho de publish desacoplado. (Alternativa equivalente, se o Builder preferir
manter o nome: manter `docker-publish.yml` apenas como arquivo deletado — mas a decisão é remover.)

`publish` declara:
- `needs: [test]`
- `permissions: { contents: read, packages: write }` (no nível do job, já que o job `test` não
  precisa de `packages: write`; mover a permissão para o job evita ampliar o escopo do `test`).
- Gate de evento/branch:
  ```yaml
  if: >
    github.event_name == 'push' &&
    github.ref == 'refs/heads/main'
  ```
  Assim, em PR e em push de branch de ciclo o `publish` NÃO roda (e em `workflow_dispatch` numa
  branch de ciclo também não publica `:latest` — ver D1b). `test` continua rodando em todos os
  gatilhos atuais.

### D1b — `workflow_dispatch` (build manual do QA) — PRESERVAR SEM FURAR O GATE
Hoje o QA usa `workflow_dispatch` em branch de ciclo para sanity do build/push. No modelo Opção B,
`workflow_dispatch` continua existindo no `ci.yml` (já existe na linha 8). Decisão concreta:

- O job `test` roda normalmente no dispatch (sanity de lint/tipos/testes).
- O job `publish` fica condicionado de modo que, em `workflow_dispatch`, ele **builda mas NÃO
  publica `:latest` e NÃO publica fora da `main`**. Implementação:
  - O `if` do job `publish` (acima) já bloqueia publish em qualquer evento ≠ `push` em `main`.
  - Para PRESERVAR a capacidade de sanity de build manual sem furar o gate, adicionar um input
    booleano ao `workflow_dispatch` e um job `build-sanity` separado (sem push), OU condicionar o
    step de push. **Decisão escolhida (mais simples e segura):** adicionar input
    `dispatch_build_sanity` ao `workflow_dispatch` e um job `build-sanity` com
    `if: github.event_name == 'workflow_dispatch'`, `needs: [test]`, que roda
    `docker/build-push-action@v6` com **`push: false`** (apenas valida que a imagem builda; nada vai
    ao registry). Esse job NUNCA chama `docker/login-action` nem gera tag `:latest`.
  - A tag `:latest` continua restrita a push na default branch via
    `type=raw,value=latest,enable={{is_default_branch}}` no `metadata-action` (mantido).

  Resultado: `push` em `main` + CI verde → `publish` (push real, tags `sha-<...>` + `latest`).
  `workflow_dispatch` em branch de ciclo → `test` + `build-sanity` (build SEM push). PR → só `test`.

### D2 — Pin do compose: **DIGEST IMUTÁVEL via `STREAMLIT_IMAGE`, default resolvível** — CONFIRMADA
Confirmo digest imutável (`@sha256:...`) como o alvo de produção, porém com a abordagem **(a)** do
enunciado para **não fabricar dado**: o Builder **não pode inventar um `sha256:` falso**, e não há
imagem nova publicada por este ciclo no momento do plano.

Implementação concreta (o Builder faz exatamente isto):
- O `image:` do serviço `streamlit` no `docker-compose.prod.yml` permanece como **override por
  `STREAMLIT_IMAGE`**, mas o **default deixa de ser `:latest` cego**. O default passa a ser uma tag
  **imutável por commit** (`sha-<commit>`), que é a tag por SHA já produzida pelo workflow — não
  `:latest` (móvel). O **pin real por digest** (`@sha256:...`) é o caminho documentado e obrigatório
  para produção, feito via `export STREAMLIT_IMAGE=...@sha256:<digest>` no runbook.
- Concretamente, trocar a linha 23:
  ```yaml
  image: ${STREAMLIT_IMAGE:-ghcr.io/kastaldy/motor-de-expansao/motor-expansao-streamlit:latest}
  ```
  por (placeholder de SHA a ser substituído — ver abaixo como obter sem inventar):
  ```yaml
  # Default NAO e mais :latest (tag movel). Producao DEVE pinar por digest imutavel
  # via STREAMLIT_IMAGE=...@sha256:<digest> (ver docs/infra_producao.md → Rollback/Deploy).
  # O default abaixo e a tag por SHA do commit corrente (imutavel por commit),
  # usada apenas como fallback rastreavel; o pin canonico de prod e o digest.
  image: ${STREAMLIT_IMAGE:-ghcr.io/kastaldy/motor-de-expansao/motor-expansao-streamlit:sha-<SHA_CURTO>}
  ```
- **Como o Builder obtém `<SHA_CURTO>` sem fabricar:** é o SHA curto (7 chars, formato do
  `type=sha`) do **commit do próprio ciclo BLK-SEC-01 que introduz esta mudança**. O Builder obtém
  com `git rev-parse --short=7 HEAD` APÓS criar o commit das mudanças de workflow/compose, e então
  faz um segundo commit (ou amend, conforme política do ciclo) ajustando o placeholder para o SHA
  real. Esse SHA corresponde 1:1 à imagem que o workflow publicará para esse commit quando ele
  entrar na `main` (tag `sha-<SHA_CURTO>`). Nenhum valor é inventado: é o SHA do commit que o git
  já conhece. **NÃO usar um `@sha256:` literal no default** (esse só existe após o push real ao
  GHCR; tentá-lo agora seria fabricar dado).
- O critério "compose fixa um digest/SHA conhecido" é satisfeito: o default vira um **SHA conhecido
  e imutável por commit** (não `:latest`), e o **digest imutável** é o pin canônico de produção
  documentado no runbook (resolvido por quem fizer o deploy, com comando exato — ver D3).

### D3 — Runbook de rollback em `docs/infra_producao.md` (modelo PULL, digest imutável)

### 1. `.github/workflows/ci.yml` — adicionar job `publish` (Opção B) e job `build-sanity`
1.1. Manter o job `test` exatamente como está (NÃO reescrever a lógica do CI; o gate só o consome).
1.2. Adicionar ao bloco `on.workflow_dispatch` um input opcional para o sanity de build:
```yaml

    branches: [main, codex-dashboard-m1-streamlit]
  pull_request:
    branches: [main]
  workflow_dispatch:
    inputs:
      dispatch_build_sanity:
        description: "Buildar a imagem (SEM publicar) para sanity em branch de ciclo"
        type: boolean
        default: true
```
1.3. Adicionar `permissions: { contents: read }` no topo (least-privilege global) OU manter sem
     declaração global e declarar por job. **Decisão:** declarar global `contents: read` e elevar
     `packages: write` só no job `publish`.
1.4. Adicionar o job `publish` (gate real, push em main com CI verde):
```yaml
  publish:
    needs: [test]
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v5
      - name: Login no GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Metadata (tags/labels)
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}/motor-expansao-streamlit
          tags: |
            type=sha
            type=raw,value=latest,enable={{is_default_branch}}
      - name: Set up Buildx
        uses: docker/setup-buildx-action@v3
      - name: Build e push
        id: build
        uses: docker/build-push-action@v6
        with:
          context: .
          file: Dockerfile.streamlit
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
      - name: Exibir digest publicado (pin de prod)
        run: echo "Digest imutavel publicado: ${{ steps.build.outputs.digest }}"
```
1.5. Adicionar o job `build-sanity` (dispatch manual em branch de ciclo, SEM push):
```yaml
  build-sanity:
    needs: [test]
    if: github.event_name == 'workflow_dispatch' && inputs.dispatch_build_sanity
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v5
      - name: Set up Buildx
        uses: docker/setup-buildx-action@v3
      - name: Build (sanity, SEM push)
        uses: docker/build-push-action@v6
        with:
          context: .
          file: Dockerfile.streamlit
          push: false
          tags: motor-expansao-streamlit:sanity
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

> estrutura. Indentação a respeitar: jobs no nível 2 espaços, steps 6 espaços, chaves de step 10.

## Estratégia de prova do gate (critério de aceite #1)

**Nível 1 — Estática (OBRIGATÓRIA, sempre):**
- Revisor confirma no `ci.yml` que o job `publish` tem `needs: [test]` E
  `if: github.event_name == 'push' && github.ref == 'refs/heads/main'` — não há caminho de push ao
  GHCR sem `test` verde. `build-sanity` tem `push: false` (não publica). `docker-publish.yml` foi
  removido (sem caminho desacoplado). Registrar: "revisão estática OK, sem caminho de publish sem
  CI verde".
- O Builder registra no handoff o trecho YAML final dos jobs `publish`/`build-sanity`.

**Nível 2 — Validação de sintaxe (OBRIGATÓRIA):** ver Validações obrigatórias (parsers YAML).

**Nível 3 — Dinâmica controlada (OPCIONAL / DIFERIDA ao fechamento humano):**
- Em branch de ciclo (NUNCA `main`): commit temporário que quebra um teste/lint, disparar
  `workflow_dispatch` (ou push na branch de ciclo). Como `publish` só roda em `push` na `main`, e
  `build-sanity` depende de `needs: [test]`, com `test` vermelho ambos ficam **skipped/não
  executados**. Mostrar nos Actions que nenhum push ao GHCR ocorreu; anotar o **run id**; reverter
  o commit de quebra. Registrar run id e link no handoff de fechamento.
- NOTA: disparar runs reais no GitHub Actions pode não ser viável para o Builder local. Por isso o
  Nível 3 é **prova diferida ao fechamento humano**; Níveis 1 e 2 são a prova obrigatória do ciclo.

## Riscos técnicos
- **Coexistência de workflows:** se `docker-publish.yml` NÃO for removido, o gap persiste (publish
  desacoplado em `push:[main]`). Mitigação: remoção explícita no item 2.
- **Permissão `packages: write`:** mover para o job `publish` (não global) evita ampliar escopo do
  `test`. Se ficar global, funciona mas é menos least-privilege.
- **`<SHA_CURTO>` no compose:** depende do commit do ciclo; resolver via `git rev-parse` APÓS o
  commit das mudanças (segundo commit/amend). Risco de esquecer e deixar placeholder → QA deve
  conferir que não há literal `<SHA_CURTO>`/`<commit>` residual no compose.
- **Não fabricar digest:** o Builder NUNCA pode escrever um `@sha256:` literal no compose/docs como
  se fosse real. Default do compose = tag `sha-<commit>` (conhecida); digest é placeholder
  `<digest>` apenas em docs com instrução de como obtê-lo.
- **`workflow_dispatch` em `main`:** se alguém disparar dispatch na `main`, `build-sanity` roda
  (sem push) e `publish` NÃO (pois `if` exige `event_name == 'push'`). Comportamento correto:
  dispatch nunca publica.
- **Guardrail §6:** nada roda no VPS via agente. Runbook é documentação; "testado" = coerência na
  revisão.
- **Inconsistência de docs:** se a seção `--build` antiga de `infra_producao.md` não for substituída,
  a doc fica contraditória com o modelo PULL. Mitigação: item 4 substitui integralmente.
