# Handoff — BLK-DIM-13 Planner → Builder

> Correção de wiring de receita no engine property-first de viabilidade. Split da
> demanda-premissa em balcão (~69%) + agregadores (~31%) com dois tickets, eliminando
> o double-count que superestima receita em ~33%. READ-ONLY sobre o M1.

## Decisões de design (Q1–Q5)

### Q1 — Contrato do split — CONFIRMADO
`demanda_premissa` sempre representa **alunos TOTAIS** (balcão + agregadores). O split
default é `SHARE_BALCAO_DEFAULT = 0.69` (constante nomeada em `viabilidade_ponto.py`).
Derivações:
- `alunos_balcao = demanda_premissa * share_balcao`
- `alunos_agregadores = demanda_premissa * (1.0 - share_balcao)`

`share_balcao` entra como **parâmetro nomeado** de `analisar_viabilidade_ponto`
(`share_balcao: float = SHARE_BALCAO_DEFAULT`), configurável mas com default rastreável
ao estudo §5 (Ultra balcão ~69% / agregadores ~31%).

Justificativa: §5 do estudo mostra que só o TOTAL escala com m²; o balcão é o segmento
de maior receita (ticket cheio R$137) e os agregadores entram a ~60% do ticket (R$82).
O p50 do toggle "usar p50" é o p50 de `alunos_total`, logo a premissa é total por contrato.

### Q2 — `grade_sensibilidade`: valores da grade são alunos TOTAIS — DECIDIDO: TOTAIS, split interno
Os valores em `n_alunos_range` (200, 400, …, 1200) passam a representar **alunos TOTAIS**
e o split é aplicado **internamente em cada célula**:
- `balcao_cel = alunos * share_balcao`
- `agr_cel = alunos * (1.0 - share_balcao)`
- `viabilidade(balcao_cel, m2, aluguel, ticket_medio, alunos_agregadores=agr_cel, **kwargs)`

Justificativa: consistência total com o contrato Q1. A grade é a sensibilidade da MESMA
premissa (alunos totais) que o operador informa; varrer balcão puro deixaria a grade numa
unidade diferente do card principal e do break-even, confundindo o usuário. A coluna de
saída `alunos` continua exibindo o total varrido (o valor da grade), preservando a semântica
visível na aba. `share_balcao` entra como novo parâmetro nomeado de `grade_sensibilidade`
(`share_balcao: float = SHARE_BALCAO_DEFAULT`).

### Q3 — break-even (`alunos_minimos_viaveis`): agregadores FIXOS na premissa — CONFIRMADO
O break-even resolve "quantos alunos de BALCÃO são mínimos para a margem-alvo", dados os
agregadores derivados da premissa. Passar `alunos_agregadores = demanda_premissa * (1-share_balcao)`
**fixo** (não escalando com a variável de busca do brentq).

Justificativa: o brentq de `alunos_minimos_viaveis` varia o 1º argumento de `viabilidade`
(= balcão). Se os agregadores escalassem junto, o break-even deixaria de ser "alunos de
balcão mínimos" e viraria um ponto fixo arbitrário. O contrato correto é: agregadores são
premissa de composição (derivados da demanda total assumida), o break-even pergunta quanto
balcão é preciso por cima dessa base de agregadores. Consistente com a doc da função
("Alunos minimos (balcao)"). Mesma lógica vale para `aluguel_teto` (ver Q5).

### Q4 — campos novos no `ViabilidadePontoResult` — ADICIONAR (com defaults)
Adicionar dois campos derivados para auditabilidade:
- `alunos_balcao_premissa: float`
- `alunos_agregadores_premissa: float`

**Restrição de implementação:** devem ser declarados **COM valor default** (`= 0.0`) no
dataclass, posicionados APÓS o campo `demanda_premissa` que tem default
(`demanda_fonte: str = DEMANDA_FONTE_PREMISSA` é o único com default hoje e está por último).
Como dataclass não permite campo sem default após um com default, há duas opções — escolhida:
**colocar os dois novos campos imediatamente ANTES de `demanda_fonte`** (que é o último, com
default) e dar-lhes default `= 0.0`. Assim:
- `analisar_viabilidade_ponto` os preenche sempre com os valores reais.
- O fixture `_fake_viab_result` em `tests/integration/test_streamlit_app.py` (linhas 5166–5184)
  **não quebra** (não passa esses campos → usam o default 0.0).

Justificativa: o valor de auditabilidade (mostrar explicitamente o split que alimentou o DRE)
supera o custo trivial de 2 campos derivados, e os defaults garantem zero quebra do fixture
de integração existente. NÃO exibir na UI neste bloco (escopo mínimo); apenas disponibilizar
no resultado.

### Q5 — `aluguel_teto` limite superior (`alug_sup`) — CONFIRMADO sem regressão
`aluguel_teto` recebe `alunos_balcao` (= premissa × share) como 1º argumento e
`alunos_agregadores=` derivado via kwargs. O `alug_sup = alunos_maturidade * ticket_medio * 2.0`
passa a usar `alunos_balcao` (menor que a premissa total). Isso **não capa o teto
incorretamente**: `alug_sup` é apenas o limite superior do bracket do brentq, e a margem
EBITDA cai com o aluguel (receita inclui agregadores + personal, mas o custo de aluguel é
linear), então o teto real fica bem abaixo de `alug_sup` para qualquer premissa realista.

Verificação: com a premissa default (balcão ~647 a partir de 938), `alug_sup ≈ 647*137*2 ≈
R$177k`, ordens de magnitude acima do teto realista (~R$25–60k). Para premissas ALTAS
(p50=2350 → balcão 1621), `alug_sup ≈ R$444k`, ainda folgado. **Não piora vs comportamento
atual** (BLK-DIM-16 trata o refino do limite superior; fora de escopo aqui).
